# Contributor instructions

[English](AGENTS.md) | [简体中文](AGENTS.zh-CN.md)

- Read [product direction](docs/en/product-direction.md), [architecture](docs/en/architecture.md) and [development](docs/en/development.md) before changing behavior.
- The core product is a Builder Agent that helps users construct, validate and revise strategy projects; cup-with-handle is an example with both genuine Builder and original execution records. Do not define generic interfaces by its parameters, judgment schema or fixed instrument list.
- The selected approach combines a domain workbench and mature coding-agent capabilities. Balance value, quality, reliability and speed; reuse for actual needs, not job keywords or an agent/framework count.
- Preserve user-owned work and saved experiment identities. Strategy changes create new versions; never rewrite existing results.
- In the current execution example, code owns arithmetic, accounting, sizing and execution; models apply the approved method to fixed candidates. The builder may propose method changes, but must distinguish implementation repairs from method revisions requiring confirmation. Ask about missing conditions rather than silently inventing rules.
- Historical execution tools obey instrument and information cutoffs; builder tools need separate project/file/data/network authorization and isolation, not unrestricted host authority. Save successful responses before parsing; never silently retry unknown billing outcomes.
- Paid calls require explicit scope and budget approval. Never call providers as part of the test suite or startup.
- Distribution has two modes of one product: a locally runnable application and a read-only interactive showcase prepared for free GitHub Pages hosting. Building either mode does not authorize publication. Do not add a hosted inference/coding backend for this stage. Local builder and execution use the operator's explicitly configured credentials; never bundle the author's keys or silently borrow a Codex login. Saved demonstrations invoke no models; missing credentials or spend authorization block live model tasks.
- The public showcase uses reviewed, saved real project records and shared UI components, not fabricated AI replies. It must work without a local backend, database or credentials. Identify saved playback clearly, omit credential forms and unavailable live actions, and provide working local-run/source links. The static preview, both Builder packages, shared viewer, screenshots, GIF and captioned video are available; final release acceptance remains separate. Repository and website publication each require approval.
- Design every page for an independent first-time user downloading the product, not for the repository owner, the coding assistant or an internal developer. Do not put conversation-specific reminders, internal deliberations, debugging notes, abandoned designs or comparisons with earlier prototypes into UI copy. A user must not need our chat history to understand a label or action. Keep necessary, actionable notices about connection state, cost authorization, operation scope, errors and genuine capability limits; do not hide them to make a demo look complete. Review new and changed UI copy against this rule in both languages.
- Keep internal capability observations and semantic-validation status out of every user-facing screen, including model settings and credential renewal, regardless of whether a private check passes or fails. Retain actionable configuration, compatibility and error messages; detailed acceptance evidence belongs in private records.
- Keep Builder projects together in My projects and use the same workbench structure in local and static modes. When a native project exists, open its real editor, model assignments, request history and build/run actions, not a read-only export wearing editor styling. Deduplicate only by explicit project identity. The original cup execution reference has one separate sidebar entrance. English presentation translations must retain inspectable original messages and must never rewrite approvals, code, results or provenance.
- Run offline tests and the frontend build before claiming a change works. See development docs for optional private-data integration tests.
- Maintain matching English and Simplified Chinese documentation and language-switch links.
- User-facing docs distinguish target product from current implementation, without internal deliberations or temporary experiment history. Documentation changes do not implement new capabilities; never present the existing example as builder-generated output.
- Keep secrets, runtime databases, raw provider transcripts, private data and local archives out of version control. Release cleanup also covers obsolete code, superseded documents, temporary scripts and internal development narratives in comments; preserve useful current source, tests, accurate docs, attribution and reviewed product demonstrations. Check dependencies before moving obsolete material to an external private archive; do not delete user projects or rewrite saved results. An ignore rule is not a security audit.
- Follow the [security and release gates](docs/en/development.md#security-and-release-gates): validate prompt-injection and execution boundaries, and separately inspect the actual publishable files, history, exports, media and container contents. Keep private plans, spend approvals and detailed audit working notes outside the public repository. Do not call a basic secret scan a complete security audit.
- Do not publish, push, choose a license or deploy a public service without approval.
- Use apply_patch for source edits. Avoid unrelated rewrites and preserve the established local-first design.
